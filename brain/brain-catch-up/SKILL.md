# Catch up

One run for everything waiting (decision 0037). It has two halves: a **read-only pass** that finds the work and every question it raises, then **one batch of questions**, then a run that finishes without asking again. Anything that becomes blocked during the run is **skipped** and listed in the report; the rest goes on. Started as "catch up unattended", it asks nothing at all: follow "Unattended" at the end, which says what changes in each step.

This skill orders the work; the other skills hold the steps: brain-sync (pull and publish), brain-apply (decisions), brain-ingest with its references (meetings, sources, attachments, the drop folder, linked repos, Documents), brain-query (reports), brain-repos (a linked repo's task rollup). Read each part when the run reaches it, and only when it has work ("What to read, and when" below). Their rules apply unchanged, whether or not this run read them, including the trust rules in the brain's AGENTS.md and brain-ingest's "What you may read, and what you may write": what the brain already holds is read only with `brain query --candidates` and `brain query --read` (spec/eligibility.md §10), never by opening, grepping or listing its files, in every step below, in every sub-agent and in an unattended run. A note the read withholds is skipped, never replaced by its file, a listing or its Notion page.

**The bar** (decision 0043): over two meetings and one capture, from "go" to the report in under 5 minutes, without the session running out of context. So each input is analysed in its own sub-agent (step 3), Notion is written in one batch at the end (step 4), and nothing already in Notion is written twice. Note the time when the user says "catch up" (or the run starts), and count the notes whose full text the run and its sub-agents read: the run logs both at the end (decision 0045).

**Modules** (decision 0048): `brain status` gives `modules`. A step marked with a module (*Knowledge*, *Orgs*, *Documents*, *Reports*, *Tasks*, *Planning*) runs only when that module is on; when it's off, skip the step and its questions without a word. Core (Inbox, Meetings, Projects, Areas, People, Review) always runs. A module that is on but whose database id is still empty (`brain modules` lists it under `missing`) is named once on the report's Needs you line: "Documents is on but its database isn't set up: say "set up documents"".

**Example rows** (decisions 0084, 0087): a row whose title starts with `Example · ` (the word `Example`, a space, the middle dot `·`, a space) is one of the Notion template's invented rows, which setup removes when it connects the brain. Nothing in the brain is ever made from one: the pull leaves it out (brain-sync step 2), step 2b skips such a Review row as brain-apply does (decision 0087), and steps 4 and 5 skip such a meeting or Inbox row as brain-ingest does. The report names how many were left out, once, under Check: "2 example rows skipped: delete them in Notion, or say "set up my brain" to remove them". An unattended run does the same.

**What to read, and when** (CC-264). Everything the run reads stays in the session and is paid for again on every later call, so read each part at its step, once, and skip it when its step has nothing this run. A sub-agent reads what its own work needs.

| Read | At | Only when |
|---|---|---|
| brain-sync "Pull" steps 1–5, "Accepted wording" steps 1–3, references/formats.md | step 1.2 | Notion is configured |
| brain-apply references/review-items.md §1–§3 | step 1.2b | a Pending Review row has item sections |
| brain-apply "Reading What to fix" | step 1.3 | the plan has `NOTE_TO_READ` or `FIX_TO_READ` |
| brain-ingest steps 2–3, references/selection.md §1–§3 | step 1.4 | a meeting is Reviewed, or a Ready Inbox row has subjects and ids or a For the brain toggle |
| brain-ingest references/sources.md, the sections for the kinds waiting | steps 1.5–1.8 | an Inbox row is Ready, a file is in the drop folder, or a linked repo has changes |
| brain-repos "The rollup (tracked-in-repo)" | step 1.8 | a found repo's kit has `tasks.mode` `tracked-in-repo` |
| brain-query "Report mode" | step 1.9, Run step 6 | the plan has reports work, or there is an Ask row |
| brain-ingest steps 4–10, references/extraction.md and cli-inputs.md, the writing reference | Run steps 2–3 | an input is ingested inline (a sub-agent reads them itself) |
| brain-sync "Push" and "Accepted wording" steps 6–9, brain-ingest references/notion.md "Publish" | step 4.1 | the run publishes |
| [references/unattended.md](references/unattended.md) | before the first command | the run is unattended |
| [references/schedule.md](references/schedule.md) | — | the user asks for a schedule |

Keep text out of the session that nothing needs: never print an input's text (a transcript, a file) to look at it when the command that takes it returns what the run uses (`brain source extract` returns the extract's passages), and when you need a few fields of a long `--json` reply, filter it (`jq`, or a short `python3 -c`). After a context summary, read again only the section you need, not the whole skill.

**Working files.** Make your own temporary folder with `mktemp -d` and keep `snapshot.json`, `plan.json` and the conversions in it; never a fixed name such as `/tmp/ub-catchup`: another session on the same machine would overwrite your plan.

Run every CLI command as `brain <command> --brain <brain> --json`. If `brain` is not found (`command not found`), install it with `npm install -g ultimate-brain`, then retry.

## 1. Read-only pass

This step changes no knowledge: no note, proposal, `brain.json`, commit, Notion page or drop-folder file. Two writes are allowed because they change nothing the user owns: `brain index` may regenerate a stale `index.md` (generated, rebuilt again later in the run), and the working files (`snapshot.json`, `plan.json`, conversions) go in a temporary folder outside the brain.

1. **Status.** Run `brain status`; run `brain index` if `index_stale`. Note `settings` (absent means `publish: ask`, `push: auto`, `unattended.max_inputs: 10`), and `unattended` (the scheduled runs since the last attended catch-up), `modules`, and which databases are configured. Each Notion part below needs its database configured; skip the ones that aren't and name them once on the report's Needs you line. **Off its working branch:** when `brain status` has the warning `BRAIN_OFF_WORKING_BRANCH`, say its message in one line and offer "fix my backup" before the read-only pass goes on (an unattended run follows "Unattended" instead) (brain-setup references/backup.md, "Off the working branch, at the start of a run"). Never create a branch, a worktree or a pull request in the brain (decision 0086).
2. **Pull plan.** Brain-sync "Pull", steps 2–4, with the snapshot and plan in the temporary folder. Read **every** configured database of a module that is on (brain-sync step 2 lists them, Goals, Key Results and Documents included; never Meetings), all pages of each, plus the Inbox rows brain-sync step 2 names. Run `sync plan` once and save `plan.json`. It holds the imports, your corrections, the decided Review rows, the conflicts, `document_requests` and `promote_requests` (*Documents*), `refresh_requests` and `report_fixes` (*Reports*), and the wording arrays `accepted_wording`, `wording_waiting`, `wording_held` and `clear_accepted` (*Documents*, *Reports*: brain-sync "Accepted wording" steps 1 to 3 say which pages to read and how; step 1 selects them from the Documents rows this step already read, when that read is complete, instead of a second query).
2b. **Review rows with item sections** (migration 0013). Read each Pending Review row's `review` object as brain-apply references/review-items.md §1 says, so `plan.json` holds `review_decisions`, `review_held`, `review_revisions` and `review_pending`. Held items and `review_revisions` go in the batch as questions or Needs you lines, never applied by guesswork. The decided items of `review_decisions` are **not questions**: the user decided them on the page (brain-apply references/review-items.md §2: no second yes). Name them in the batch's opening line with what each will write ("I'll apply what you submitted on Acme launch review: a · launch date → 2027-04 (your value), c · rejected"); when nothing else blocks, that line is the whole batch and the run starts.
3. **What to fix on Review rows.** For each `NOTE_TO_READ` and `FIX_TO_READ` conflict, read What to fix against its proposal and decide what it means (brain-apply, "Reading What to fix"). Write down the decision you would apply ("a: launch 2027-03"), or the question it raises. A `FIX_WITHOUT_TEXT` row goes in the batch as a question: "Acme launch review: Fix, but What to fix is empty: what's wrong?"
4. **Meetings** *(Notion)*. Brain-ingest steps 2 and 3, up to the duplicate check: the Reviewed meetings, oldest first, and each one's pre-check blockers. For a summary with subjects and ids (escaped or not, selection.md) or a For the brain toggle, also brain-ingest references/selection.md §1–§3 in read-only form: its `extract-plan` blockers (`SELECTION_UNMAPPABLE`, `SELECTION_UNREADABLE`, `UNNUMBERED_LINE`), a meeting with minutes but no transcript (selection.md §2 step 1: not a question, the user fixes it in Notion; name it under Needs you with that step's fix, word for word, and leave the meeting Reviewed) and an input that is unconfirmed or too fresh (the page edited less than 2 minutes before the run, `TOO_FRESH`, a label of this skill) are batch questions, and the preview of what will be copied belongs to the batch. In lean minutes (a For the brain toggle, decision 0079) the preview also names the quick follow-ups that become Tasks, with their text (default: created; to keep one out the user ticks or deletes it on the page, and the run reads the page again before writing it, references/selection.md §4). A meeting the brain already ingested and that is Reviewed again is a **re-read** (decision 0045): the user fixed its minutes; say so in the batch ("Acme sync, read again: only what changed"). Minutes files are ingested only when the user names them, never looked for.
5. **Inbox.** The rows with Brain Status **Ready**, and only those (decision 0048): never a New or Done row, whatever its Kind or age. A capture or voice note with subjects and ids (escaped or not, selection.md) is read like a selected meeting (references/selection.md); a New row is unconfirmed and never taken, and you never set a row to Ready. Oldest first, each with its pre-check blockers (brain-ingest references/sources.md, "capture"). A Ready row with a Brain ID is a **re-read**, as for meetings. A row with Project or Area set needs no project question. A row's **Only keep** and **Document asked** come with it; an empty Only keep is never asked about (decision 0049). A capture that repeats a source the brain already has: default skip, naming that source and linking its row (sources.md, "Pre-check").
   **Ask rows** *(Reports)* (Kind = Ask, Brain Status New or Ready) are requests for a report, not captures: never ingest one; note its question (the Name) and its Project or Area for the report ("Run", step 6).
   **Attachments** on the rows taken in and the Reviewed meetings: list each file (sources.md, "Attachments"), all selected by default. On a row with Document asked ticked, each file becomes a Document (step 1.7).
6. **Drop folder.** The queue and its question (sources.md, "The drop folder", steps 1–2: whether to keep each file as a document, and whether one is a new version), without moving anything.
7. **Documents asked for** *(Documents)*. From `plan.json`, each `document_requests` item (a row already taken in whose Document asked box is ticked) and each `promote_requests` item (a decision whose Promote asked box is ticked), plus the Ready rows of step 5 with Document asked ticked and the drop-folder files the user may keep. An item with `existing` is already done: the run only clears its box. A Promote asked the plan ignored as `NOT_REVIEWED` keeps its box ticked and waits for the note's approval; name it once under Check. None of these asks a question; name them in the batch's opening line ("I'll also keep 2 documents and promote 1 decision").
8. **Linked repos.** For each entry of `repos` in `brain status`: `brain repo changes <name>` (sources.md, "Linked repos"). A repo with `found: false` is named on the Needs you line. More than 10 files: they go in the batch as a list, default all.
   **Their task rollups.** For each found repo, `brain repo show <name>`: when its `kit` has `tasks.mode` `tracked-in-repo`, build its rollup now with the brain-repos skill, "The rollup (tracked-in-repo)", step 1 (`brain repo tasks <name>`, with the issues fetched for GitHub or GitLab), whether or not it has changed files, and keep `toggle` for the publish (step 4.1.1b). It writes nothing and asks nothing. A refusal or a failed fetch writes no rollup and keeps the old one: say why under Check.
9. **Reports** *(Reports)*. From `plan.json`: each `refresh_requests` item, and each `report_fixes` item with the proposals its text would become (brain-query, "What to fix on a report"), written down like a Review row's What to fix. Also each report whose last `fixes` entry lists only proposals now applied, rejected or closed, and that wasn't refreshed since: it is due a refresh.
10. **Accepted wording** *(Documents, Reports)*. From `plan.json`: each `accepted_wording` item (text the user accepted, to be imported exactly: brain-sync "Accepted wording", step 4 shows its diff), each `wording_waiting` row (named under Needs you with its reason in plain words) and each `NO_BASELINE` row, accepted (`wording_waiting`) or not (`wording_held`), as a question (brain-sync "Accepted wording" step 8: an accepted one may adopt Notion's text; an unaccepted one is told to click Accept first; adopting Git is a paste by the user). A `refresh_requests` item marked `wording_blocked` does not run: name it ("Acme report: resolve the text in Notion first"); its Refresh asked box stays ticked.
11. **The backlog.** `brain proposal backlog --dry-run`: the Review notes rows the run will write once for notes from before 0.4.0. They need no question; name them in the batch's opening line ("I'll also write 2 Review notes rows for older notes").
12. **Pending proposals in chat.** Without a Review database, run `brain proposal list --status pending,approved,edited,rejected`: these go in the batch as chat decisions (brain-apply, chat mode, steps 2–3).
13. **Your identities.** If `brain.json` has no `owner.person`, add the identities question (brain-connect-notion, step 6).

The pass is done when every input that is waiting has been found and each of its blockers is written down as a question or a default.

## 2. One batch of questions

When `unattended.catch_up` in `brain status` isn't null, open with the scheduled runs since the last attended one, as one line: "Since last time: 4 scheduled runs, 6 inputs in, 1 skipped, 1 Fix waiting, 1 failed: Notion login". Say "Backlog growing: run more often or raise the budget" too when `unattended.backlog` is true. Then ask once, in one message, numbered and grouped by input, each with the answer you will use if the user says "go" (the **default**):
- sync conflicts (`BOTH_CHANGED`, `MISSING_REQUIRED`, `UNRESOLVED_RELATION`, …) and your corrections, as brain-sync step 5 shows them;
- each What to fix you read, as "Acme sync: 'all except b' → approve the rest, b waits in a row of its own" or "Acme sync: Fix 'a: March' → launch date 2027-03";
- each meeting's and input's pre-check blockers;
- the pending proposals, as brain-apply's chat list (default: leave them pending);
- each accepted text to import (*Documents*, *Reports*), as "Login page: import your accepted write-up? (+12 −3 lines; shown below)" with the diff of the whole file under it (default: yes), and each row with no baseline, as "Acme report: Notion's text and the brain's differ; keep which? (default: leave both)";
- the drop-folder list, all files selected, each with "keep as document? no / all / only …" (default **no**) when Documents is on;
- each attachment, all selected, and each linked repo's files when there are more than 10;
- each likely new version (default yes);
- *(Reports)* each Ask row, as "Report on <its question> (default: yes)"; each Report row to refresh, and each report What to fix with the proposals it becomes ("Acme launch report: 'Lucía left Acme in June' → Lucía's org: Acme → none, from June");
- the identities question (default: skip for now, ask again next catch-up). The user's answer is their approval of those aliases;
- with `settings.publish: ask` and Notion configured: "Publish to Notion at the end?" (default yes). This is the run's only publish question. Without Notion there is nothing to publish: leave it out.

When nothing blocks, don't ask: say what you will do in one line and start. When nothing is waiting at all, give the report with `Done: nothing waiting` and stop.

## 3. Run, in this order

Every note, Document, report and Review text this run writes follows [the writing reference](../brain-query/references/writing.md) (decision 0081 §7); give its path to each sub-agent that analyses an input.

0. **The backlog, once** (decision 0041): `brain proposal backlog`. On a brain from before 0.4.0, the first run writes one Review notes row per source over its `draft` notes; every later run writes nothing. Commit any rows it wrote: `review: <n> Review notes rows for the backlog`.
1. **Pull and apply.** Commit anything the run has written so far: Review decisions are applied as one journaled operation that commits itself and refuses a dirty tree. First settle accepted wording in `plan.json` as brain-sync step 6 says: re-read and add `verified` to each `accepted_wording` item the user said yes to, move every one you will not import (declined, or changed since the plan) into `wording_held`, add the adoptions the user chose. Verify each decided Review item too, as brain-apply references/review-items.md §3 step 1 says (re-read its page, plan again, set `verified` on the items that are unchanged, drop the others as `CHANGED_SINCE_PLAN`). Then **one** `brain sync apply --input plan.json` (brain-sync steps 6–8, with 6b's Notion writes; never apply the plan twice), then with `brain apply --input <file>`: the decisions you resolved from What to fix (brain-apply, "Reading What to fix"), the chat decisions from the batch (`decided_by: chat`), and the identities. Carry out the `notion_writes` of every apply and settle them (brain-apply, "Notion writes"). For the identities, run brain-connect-notion step 6 in full, with the batch answer as the user's approval: the owner-ruling source and, when the owner's person note exists, one `add_link` alias proposal per value applied with `decided_by: chat`; when it doesn't, a new person note (`brain note new`) carrying the aliases; then `brain config set owner.person '"<per- id>"'`. Rebuild and commit as brain-apply "Finish", steps 1–3. Conflicts the user didn't answer stay conflicts.
1b. **After the apply, for each accepted Document or report imported** *(Documents, Reports)* (its text is already in Git; Accepted is cleared at publish, step 4b): for each Document, **Related knowledge.** Run `brain query --candidates "<its title>"` and with the names of its project, people and decision, read the notes that bear on it with `brain query --read`, and propose the useful ones as one `add_to_note` proposal on that Document: `brain proposal new` with `kind: add_to_note`, the Document as `target`, `source` = `notion:<the Document's Notion page id>` (the CLI refuses a proposal without one), `passages` = the ids of the notes it lists, `title` "<Document title>: related knowledge", `content` a section `## Related knowledge` with one list item per note, `[title](relative path)` as the read returned them (a note in its awaiting-cleanup form by its `cite` label, with no link) and the reason it helps, written from what the read returned, and `why` naming the Document. Cite only notes the read returned; propose nothing when none helps. The accepted text stays as it is: approving appends the section after it. A change to any other note is its own proposal. For a **report** nothing is proposed (reports are not proposal targets, decision 0057): add one line to the report's entry under **What came in** naming useful knowledge only the brain has ("Not in the accepted refresh: ..."), and offer a full refresh. Commit: `documents: import accepted wording (<n>)`.
2. **Selected inputs are extracted first and analysed inline.** A meeting or capture with subjects and ids (escaped or not, selection.md), or with a For the brain toggle, is written as an extract before it can be analysed (brain-ingest references/selection.md §2–§4: preview and confirmation in the batch, then `brain source extract`, which commits), and its analysis reads the extract's `passage_hash`es, so it runs inline, one input at a time, like a re-read. The rest of this step is for the other inputs.
   **Analyse each other input in its own sub-agent** (decision 0043): each meeting, Inbox row (with its attachments) and chosen file. A run with one input, or inputs of a page or two each, can analyse them inline instead, one at a time: the sub-agents are there to keep long inputs out of the run's context. Inline is also the way when the session can't start sub-agents. Give each one the brain path, the input (or how to read it), its batch answers, its Only keep and Document asked, and the brain-ingest skill with its references (its rule on what it may read included: it matches and loads existing notes only with `brain query`, never a file of the brain), and have it run, read-only, brain-ingest steps 4–6 and the dry runs of step 7, then return the `note new` batch (with any Documents, brain-ingest references/extraction.md "Documents"), the `proposal new` batch (with the input's one `review_notes` and any `answer`), the task items and the report lines. A sub-agent never runs a write, a commit or a Notion call. Run up to 4 at a time. A **re-read** is analysed inline in step 3 instead: its diff needs the new source written first (brain-ingest references/sources.md, "Re-reads and new versions"), and the changed lines are short.
3. **Write them, one input at a time,** in the order of step 1 (meetings oldest first, then Inbox rows, then files): before each batch, check its new notes against what the inputs before it wrote (`brain query --candidates "<the new note's title>" --types <its type>` after `brain index`): a person, project or learned Document another input already created is linked to that note instead of created twice. Then brain-ingest steps 7.3–10 (the real `note new`, `proposal new`, rebuild, check, log, commit). On `INPUT_INVALID` from a path that changed since the dry run, run the dry run again and fix the links.
4. **Linked repos:** their files are inputs of steps 2–3 too; after a repo's last file, `brain repo record`, unless a file failed or the user wants some later (sources.md, "Linked repos", step 4).
5. **Documents** *(Documents)*, for the inputs already in the brain (step 1.7; the inputs taken in this run wrote theirs in step 3), with brain-ingest references/extraction.md "Documents":
   1. each `document_requests` item without `existing`: with `only_keep` null, one `whole` Document per file in `files`, or of `source` when `files` is empty; with `only_keep` set, one `part` Document of what it names, in a new `review_notes` for that source;
   2. each `promote_requests` item without `existing`: one `promoted` Document seeded from the note as `brain query --read` returns it; a note returned with `restricted: true`, or withheld, waits (extraction.md "Documents": named under Needs you, its box left ticked);
   3. what the user asked in chat ("also keep the budget from the Acme doc"): a `part` Document from the source the brain already has, copied from its latest version as `brain query --read <src-id>` returns it (an older version is withheld: never copy one from its file).

   `ALREADY_KEPT` in `skipped` is fine: that whole Document exists. Rebuild and commit: `documents: <n> kept, <n> promoted`. Each item written, skipped as `ALREADY_KEPT` or carrying `existing` has its box cleared in the publish (step 4.1.4); one that failed keeps it, so the next catch-up tries again.
6. **Reports** *(Reports)*, with brain-query "Report mode":
   1. each report What to fix: its proposals and `brain report fix` (brain-query, "What to fix on a report"). Commit: `report: fix <title>`;
   2. each refresh: a Report row with Refresh asked ticked, or a report whose last `fixes` entry lists only proposals that are applied, rejected or closed (one recorded with `--record-only` waits). **Skip every report that `plan.json` names in `wording_waiting`, `wording_held` or `accepted_wording`, and every `refresh_requests` item marked `wording_blocked`; this includes a refresh that is only due** (Refresh asked stays ticked and the report goes on the Needs you line: "resolve the text in Notion first"). Commit: `report: refresh <title>`;
   3. each Ask row the user didn't decline: a new report with `asked_in` = the row's page id, its Project and Area. Commit: `report: <title>`.

For each input, publishing waits for step 4 below. **Skipped, not asked:** an input whose ingest raises a new question or fails is left as it is (the meeting stays Reviewed, the row Ready, the file in the queue) and goes on the report's Needs you line. The one hard stop: a lint error in a file this run wrote. Stop the run there, commit nothing more, and report.

## 4. Publish, push, report

1. **Publish** (when `settings.publish` is `auto`, or the user said yes), once for the whole run, following brain-ingest references/notion.md "Publish" for each write, in this order. Run `brain views` first, so the project and area Briefs are current:
   0a. *(Selected inputs)* **Exclusion cleanup, before the pages:** after a new extract version that suppressed or re-included paragraphs, `brain source cleanup-propose --page <id>` (once per input; `PENDING_EXISTS` means it is already waiting; `NOTHING_TO_CLEAN` needs nothing) and commit it (`review: exclusion cleanup`), so step 1 publishes the new row. Unattended this is an addition; nothing is removed.
   0. *(Review rows with item sections)* **Write back** as brain-apply references/review-items.md §4 says: the summary block, only the item sections that need something the user must see (a drafted revision, a changed base), each only if it still equals what you read; then clear Decided, Decided at and Accept all under the same guard. Never rewrite a Review body.
   1. **Pages:** `sync render --changed --plan plan.json`, write every item (the one read-back allowed after a write: a Document or report body, brain-sync "Accepted wording" step 6, recorded as `@notion_body`) (pending relations: publish and record those first, then render again, until no item is pending), `sync record`. **Every render of the run carries `--plan plan.json`, the re-renders included**: without it nothing holds back a Document or report whose Notion text is waiting, and a properties-only write to an accepted page would move its last-edited time and make a fresh Accept look stale. With it, only the text waits on a page that is not accepted: its item has its properties and `body: null` (write them; no read-back), and an accepted page has no item. This publishes the notes and Documents you have approved (a draft stays in its Review row until then and never gets a page if you reject it, decision 0071; an item with empty `properties` only waits for a note this render creates: write nothing for it), the proposals, the meetings' relations, every source's Inbox row with its digest, the report rows (then each Ask row's Brain Status to Done), the cleared Refresh asked boxes, the project and area Briefs, a question's Status = Open, and the Review rows decided more than 30 days ago (`action: trash`, moved to Notion's trash; decision 0045). Write in parallel, up to 10 at a time, and never read a page back after writing it, **except** the one read-back of a Document or report body described above (brain-sync "Accepted wording" step 6). If that read-back fails, record the page with `"@notion_body": null` (a null removes the old baseline: the next run holds the page, row 9, until the user adopts a side; this includes a previously published report just refreshed). If the record itself fails, say so on the Needs you line. **Every write carries its final content:** never create a page or write a body with placeholder text to fill in later (brain-ingest references/notion.md, "One write, final content").
   1b. **Repo task rollups:** write each rollup of step 1.8 on its target page, as the brain-repos skill, "The rollup (tracked-in-repo)", step 2 says (the `Repo tasks · <name>` toggle, replaced or appended; never read back). A target with no `notion` page yet gets none: name it under Check. Count them on the Done line ("2 repo task lists updated").
   2. *(Tasks)* **Tasks,** now that their projects and Inbox rows exist: `sync tasks --meeting` for each ingested meeting of the old kind and `sync tasks --source` for each ingested source with owner tasks and for every selected input, meetings included (brain-ingest references/selection.md §6); create each returned item once; `sync record` its page ids. ## Unattended: "catch up unattended"

The prompt a schedule runs (see "Run on a schedule"), or the user by hand. Nobody is there to ask: every question takes its default or skips its input, and the run interprets no text of the user's (decision 0051). **Before its first command, read [references/unattended.md](references/unattended.md)** and follow it: it says what changes in each step, the defaults that replace the batch, the budget, the report, the log line and the Catch-up row. An attended run never reads it.

**Off the working branch: stop at once** (decision 0086 §2, spec/cli.md §6.1). The run's first command is `brain status`. When its `branch` has `on_working` `false` or `working` `null`, the run stops there and writes nothing anywhere; its last line of output is exactly the one the reference gives (`Not run: off-working-branch. …`).

## Run on a schedule

When the user says "run catch-up every morning" (or "twice a day", "on weekdays"), read [references/schedule.md](references/schedule.md) and follow it: what to ask once (times, days, a full model id), what to offer, `brain schedule install`, and how to check and stop it. Other schedulers are there too.
